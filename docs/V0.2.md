# V0.2 development / 开发与验收

V0.2 is an early development increment, not a stable Release. Old Android acceptance is deferred; it is not required to start this branch. / V0.2 为开发增量，旧安卓真机验收继续待办。

## Contracts / 数据契约

`POST /api/v2/observations` accepts the existing write token and Observation v2:

```json
{
 "schema_version": 2,
 "provider": "system",
 "connector_id": "linux-host",
 "entity_id": "local-host",
 "category": "system",
 "source": "linux-proc-statvfs",
 "mode": "real",
 "status": "ok",
 "collected_at": "2026-10-20T00:00:00Z",
 "expires_at": "2026-10-20T00:10:00Z",
 "sensitivity": "private",
 "metrics": [{"key":"cpu.used","value":25,"unit":"percent"}]
}
```

The JSON is a schema example, not a live observation. Timestamps require timezone, normalize to UTC, and expiry follows collection. Unknown metric values are null, never zero. Nonfinite numbers, duplicate metric keys, invalid percentages and future observations are rejected. Provider capabilities are allowlisted (`codex`, `chatgpt`, `system`); category reserves all five modes without claiming their connectors exist. Sensitivity is metadata, not a public-access grant: all endpoints require a read capability. Field-level public projection is still planned.

`GET /api/v2/observations?mode=real` returns latest records for each authorized stream. `GET /api/v2/history?provider=system&mode=real&limit=20&before=<id>` returns newest ingested records first with `next_before`. Limit 1–500; maximum 1,000 records per provider/connector/entity/mode stream and 128 streams per provider. History beyond retention is deleted; this is a bounded recent history, not indefinite archival. An earlier timestamp cannot replace a newer stream observation; repeats at the same timestamp are idempotent. History and latest endpoints apply the same device/token/session scopes and revocation as v1. Existing quota-only devices do not acquire system access. Legacy global read, if explicitly enabled, is broad access including system observations.

v1 quota ingest/read remains supported; accepted v1 quota snapshots also populate v2 history. v2 ingest does not synthesize v1 quota windows. Existing timestamps, reset countdowns and demo boundaries remain unchanged. Latest history entries migrated from v1 are one per current provider/mode: unavailable older history is not reconstructed.

## First system connector / 首个系统连接器

```sh
# Run on the Linux machine whose metrics you want to collect, outside a container
PIXORA_SYSTEM_ENTITY=my-linux-host pixora-collect --plugin system --once
# Long running: same configured HTTPS server and write credential as other collectors
PIXORA_SYSTEM_ENTITY=my-linux-host pixora-collect --plugin system
```

Linux `/proc/stat` sampled over 250ms gives CPU utilization; `MemAvailable/MemTotal` gives memory used; `statvfs('/')` reports root filesystem occupancy using free blocks (reserved free blocks count as free). No remote SSH, hostname, process details or credential discovery. If run inside Docker it describes the available kernel/filesystem view and is **not** a verified host/cgroup usage report. macOS and Windows return explicit unavailable; they do not fabricate Linux metrics. Collection target is an administrator-chosen opaque ID. This is a Linux host connector, not a PVE API implementation.

Provision a separate read device when needed:

```sh
pixora-device create --name system-screen --provider system --mode real --days 30
```

Raw provisioning output is private. Use HTTPS pairing as with v1. Select System monitor in display settings; overview includes the private system widget. Shared-screen layouts exclude system observations. The widget displays source, target, timestamps, expiration and history; it never represents missing values as zero.

## Migration and rollback / 迁移回滚

Stop concurrent upgrade processes and ensure disk space first. Application startup checks SQLite `user_version`. Before migrating an existing DB it creates an online backup beside it named `pixora.sqlite.pre-v2-<UTC timestamp>`, permissions 0600. The migration creates an additive observations table/index and backfills current v1 snapshots in one transaction; v1 device/session/snapshot tables stay intact. Failed migration rolls back and retains the backup. Backups contain private observations and authorization digests: keep them private and manage retention explicitly.

Rollback procedure:

1. Stop the application and all writers; retain the failed DB, including its WAL/SHM, as a private diagnostic copy.
2. Run `python scripts/restore_database.py <pre-v2-backup> <NEW-database-path>`; the tool refuses to overwrite anything and validates SQLite integrity.
3. Configure the previous v0.1 image to use the NEW restored DB path/volume. Do not mix old WAL/SHM files with it.
4. Start the previous image and verify health, quota reads, device authentication and fresh collection before resuming normal use.

Rollback restores state at backup time; all later observations and device/session changes are lost. Never apply backup restoration to a running production database. Full disk recovery and cross-version forward migration beyond v2 are not claimed.

## Acceptance / 验收

Automated tests cover v1 backfill and untouched tables, idempotent startup, rollback to a new DB, failed migration atomicity, history retention/pagination, replay rejection, scope/expiry/revocation, missing/nonfinite values and shared-screen privacy. Deployment results are recorded separately; local tests alone are not proof of production or physical device acceptance.
