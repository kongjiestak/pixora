# V0.4 first increment: Orbit profiles and device policies

[English](V0.4.md) | [简体中文](V0.4.zh-CN.md)

Status: **Early Development / 0.4.0.dev2**. This increment adds a constrained Orbit editor, not a free-form dashboard builder. Physical-phone acceptance is tracked separately from browser tests.

## Display and synchronization

Settings → Orbit layout edits clock/weather visibility, primary vs weekly center and comfortable/compact spacing. Preview is immediate. Preferences are stored per scoped device ID in this browser only, contain no token/data and survive reopening. Blocked storage is reported. Export contains only the four layout fields. A layout never grants data access.

`GET /api/v2/device-config` returns only the authenticated scoped device's name, allowed provider set, recommended profile, revision, update time and public-only flag. It has no device-facing write method and refuses global legacy tokens. Existing devices start at revision 0 with the accepted Orbit defaults. Server recommendations are checked during the 30-second web read; a local override remains until Restore server recommendation. Language/motion remain browser-local.

Administrator publication is local CLI only:

```sh
pixora-device --db /data/pixora.sqlite list
pixora-device --db /data/pixora.sqlite inspect DEVICE_ID
pixora-device --db /data/pixora.sqlite configure DEVICE_ID --profile examples/device-profiles/compact.json
pixora-device --db /data/pixora.sqlite configure DEVICE_ID --policy examples/device-profiles/system-cpu-only.json
```

Replace example connector/entity IDs with actual authorized IDs. An exported layout JSON can be used as `--profile`. `configure` preserves the other half if only one file is supplied, validates strictly, and increments the revision atomically. Configuration files are capped at 16 KiB. `inspect`/`list` do not output raw tokens. Expiry/revocation continue to apply; no Internet-facing administrator API was added.

## Restrictive policy contract

- `rules: null` (default): preserve original provider/mode grant. `rules: {}`: return no providers. A nonempty map allowlists providers, intersected with the original token grant; CLI rejects attempts to expand it.
- Each rule optionally allowlists `connectors`, `entities`, `metrics`, `windows`. `null` means unrestricted within the original grant; `[]` denies all for that dimension. Exact matches, no regex/globs.
- `entries`: `full` (default), `titles` (strip detail and URL), `none`. Standard authorized envelope metadata (entity/connector/source/status/timestamps) remains visible. This is not an arbitrary JSON-field ACL.
- `public_only: true` filters out all observations whose producer classification is not public; v1 snapshots have no public classification and are withheld. Only trusted write-token collectors may classify observations. The browser's shared toggle additionally signs out/hides all private content; it is not a server policy editor.
- Policies apply to v1 quota reads, v2 latest and v2 history, for Bearer **and existing Cookie sessions on every request**. History stream filters are applied in SQL before pagination; metric/entry projections apply afterward. Unauthorized content is not delivered and then hidden in CSS.
- V1 quota maps to connector `quota-v1`, entity `default`; `windows` and `metrics` intersect its window names. V2 uses those names as metric keys. Restricting one window does not relabel the surviving weekly quota as a primary quota.

## Migration, rollout and rollback

`device_profiles` is an additive table. Original device rows, token digests, scopes, sessions and observation retention remain unchanged. Back up SQLite with its backup API and check integrity before deployment. Existing devices without profile rows preserve existing reads. Test policies with an isolated/temporary device; do not change phone grants as an upgrade side effect.

**Privacy-sensitive rollback:** a pre-V0.4 server ignores the new policy table. Before reverting to it, revoke every active device with restrictive policies (or retain a V0.4-compatible server); otherwise the original broad grants would become readable again. Restore a database only with an explicit recovery plan, because old snapshots also restore old revocation/session state. A profile-only recommendation is not a restrictive policy.

## Remaining V0.4 work

Web administrator device inventory/pairing/revocation, authorized remote profile publication, multi-screen assignment and richer compositions are future work. Device display tokens remain read-only. No credential/control capability is added. Stable release, arbitrary drag/drop editing and complete field-level policy tooling are not claimed.

## Theme increment (dev2)

Profiles add `theme` (orbit/paper/amoled/aurora), `accent` (mint/blue/amber/violet), `text_size` (standard/large) and `appearance` (theme/light/dark/auto). Old four-field profiles acquire Orbit defaults without rewriting stored rows. Paper defaults to light; other presets default to dark. AMOLED is pure black only in dark mode. Follow-system responds to media-query changes while open. Text size adjusts the Orbit display; normal browser zoom remains available.

The shared token palette covers the display, settings, controls and status colors. Aurora adds a subtle gradient with an optional 18-second compositor transform; motion off, background-page state and reduced-motion stop it. Other themes do not use this background effect. Power use has not been measured. Theme/accent light/dark text palette tests require 4.5:1 contrast; this is not a full accessibility certification. No external fonts/assets or new remote permissions are required.

Export/local save/server recommendation retain the new fields. See `examples/device-profiles/aurora.json`. A server-published profile with these fields cannot be read by a strict dev1 profile parser. Before rollback, back up and convert its profile JSON to the original four fields while preserving the policy and device grants, or retain a dev2-compatible server. Merely changing to an old image is not a validated rollback.

## Selectable weather city

The profile adds nullable `weather_location` (Open-Meteo/GeoNames positive place ID). Null uses the administrator's existing collector city; users can search/select another city per browser, export it or publish it in a server recommendation. Same-named results show region/country/time zone. No device geolocation, coordinates or caller credentials are forwarded from the browser to the weather provider. City names/IDs and provider-resolved city-center coordinates are sent to the fixed Open-Meteo endpoints.

Authenticated read-only endpoints: `GET /api/v2/weather/locations?name=Houston&language=en` and `GET /api/v2/weather/PLACE_ID?language=en`. Both require real weather scope and honor restrictive connector/entity (`place-ID`), metric and entry policies. Public-only devices cannot use private city observations. Geocoding results are public place metadata, filtered to allowed entities. No Internet configuration write route is added. City forecasts are on-demand and memory-cached, not inserted into historical observations.

The cache is bounded to 256 keys, with at most four pending cache loads. Forecasts share a 10-minute cache across screens; locations cache for a day. Search is limited to ten requests/minute/device, weather cache misses to six. Upstream responses remain bounded, use fixed HTTPS hosts, do not follow redirects and receive no device credentials. Search/forecast failure is explicit and does not stop quota refresh; switching city clears the old city's weather first. Weather model/forecast time uses the selected city's IANA zone (including DST); the main clock and collection receipt presentation remain device-local. Attribution: [Open-Meteo / GeoNames geocoding](https://open-meteo.com/en/docs/geocoding-api).

Administrator collection also accepts `PIXORA_WEATHER_TIMEZONE` (default Asia/Shanghai). This does not replace per-screen city selection.
